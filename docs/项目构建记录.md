# 项目构建记录

- 项目：v2rayN VLESS 节点批量生成与 Xray 实测工具（`VLESS-Workbench`）
- 记录区间：2026-11-02 首次提出需求 → 2026-11-05 打包发布
- 参与者：用户（需求与实测反馈）、主协调助手（拆解、验收、对外汇报）、编码会话（实现与自测）
- 记录口径：本文依据最终代码、README、`docs/代码结构说明.md`、自检产物与发布文件整理；没有保留完整逐条对话原文，涉及“用户验收”的段落以后续需求变更和实际操作为准，不虚构原话。

## 1. 缘起与初始设想

2026-11-02，用户提出一个在 Windows 10/11 本地运行的中文工具：批量生成 v2rayN 可用的 VLESS 节点，调用 Xray 内核做真延迟与下载速度测试，最后输出可导出的结果。初始目标是单机、本地、命令行菜单可操作，并把关键参数收进配置文件。

最初的五步流程是：

1. 选择国家/地区 → 生成 FOFA 查询语法 → 自动搜索并下载结果文件；
2. 选择下载文件，提取 `IP:端口`；
3. 套用用户给出的 `vless://` 示例，只替换地址与端口，批量生成节点；
4. 为节点生成 Xray 配置，启动内核做真延迟与下载速度测试；
5. 输出排序后的结果，保存 CSV/JSON，并可导出纯 `vless://` 链接给 v2rayN。

初始设想中还包括 FOFA 官方 API 与网页采集两条路径、email + key 凭据、Cookie 兜底、`--setup` 凭据向导，以及“每个节点独立 Xray 进程”的测试模型。后续这些设想有一部分被实际使用推翻，下面按日期记录。

第一天确定的基本边界：

- 未配置 Xray 或 FOFA 凭据时，程序不能崩溃，要给出明确提示；
- 支持手动导入已下载文件，跳过自动采集；
- 必须有离线自检，在没有真实内核和真实节点的环境下也能跑通“提取 → 生成 → 测试 → 导出”；
- 失败原因要分类，退出时要清理临时配置与子进程。

## 3. 阶段演进

### 3.1 2026-11-02：第一轮 CLI 与离线自检

**用户要什么**

一个能实际运行的 Windows 本地程序，而不是方案或伪代码；优先 Python 3.10+；中文命令行菜单；配置集中；没有 FOFA 凭据和 Xray 内核时也要能说明缺什么，并能用模拟模式自检。

**谁怎么判断**

编码会话先按模块拆分：FOFA 采集、内容提取、节点生成、Xray 测试、结果输出、菜单入口。主协调助手重点检查三件事：没有凭据/内核时是否优雅失败；临时配置和子进程是否清理；自检是否能覆盖主链路。

**做了什么**

- 建立 `vless_tool` 包与 `main.py` 入口，配置、日志、提取、生成、测试、导出分文件；
- 实现 FOFA API 请求、粘贴导入、本地 HTML/JSON/CSV/TXT 解析；
- 实现 `vless://` 参数解析、地址端口替换、节点命名；
- 实现单节点 Xray 配置、本地 socks/http 入站、延迟与测速；
- 实现 CSV/JSON 与 vless txt 导出；
- 加入 `--selftest`，用示例数据与模拟内核跑通主链路。

**结果**

提取、生成、模拟测试、结果保存、链接导出在无网络、无内核条件下可跑通。缺参链接会一次列出缺少的 UUID、`encryption`、`type`、`security` 等项。

**暴露的问题与解决**

1. FOFA API 路线成本高于预期。免费账号字段权限、翻页额度、Key 获取和登录态都不稳定；真实查询往往要人工确认。用户实际改为“自己在 FOFA 网页搜索、手动下载资产”。
2. 因此第一轮为账号/API Key 做的凭据向导整套删除：`credentials.py`、`--setup`、菜单项、配置中的 `email/key/session` 字段全部移除。最终 `fofa` 配置只保留查询模板。
3. “每个节点独立 Xray 进程”在节点数上来后启动开销过大，这个模型在下一阶段被共享内核池取代。

**用户验收结论**

用户接受“手动搜索 + 手动导入/下载”的路线，不再要求工具保存账号或 API Key。第 1 步从“自动采集”改为“生成本地查询语句 + 打开搜索页 + 导入结果”。

### 3.2 2026-11-03：Web 界面与共享内核

**用户要什么**

命令行可用，但批量操作、表格浏览和导出在网页里更直观；希望保留 CLI，同时有一个双击可用的本地界面。

**谁怎么判断**

主协调助手先要求“业务逻辑不复制”：Web 和 CLI 必须共用提取、生成、测试、导出模块。编码会话先做页面原型，再由用户按实际使用判断信息密度和操作路径。

**做了什么**

- Web 界面第一版是参考 PEN 风格自研页面，后来整体放弃，改为在 Cloudflare EDT 导航页存档基础上改造；
- 最终运行页面是单文件 `app/web/index.html`，CSS/JS 全内联，页面呈现六个可见步骤：FOFA 搜索 → 导入资产 → 提取预览 → 生成节点 → 测试 → 结果与导出；
- CLI 仍是五步菜单；Web 的“FOFA 搜索”和“导入资产”在业务层都属于导入阶段；
- 后端增加 Flask 路由、waitress 承载和 SSE 测试进度流；
- 把“每节点一个内核进程”改为共享内核池：每 `test.kernel_batch`（默认 50）个节点共用一个 Xray 进程、一份配置，每个节点一个本地入站端口；
- 延迟并发与测速并发拆开：延迟默认 50，测速默认 5。延迟是短连接握手，测速会抢带宽，不能使用同一并发值。

**100 节点实测**

同一批 100 个节点，在同一台机器上得到：

| 配置 | 耗时 | 内核进程数 |
| --- | ---: | ---: |
| 并发 4 / 每批 1 | 84.91 秒 | 99 |
| 并发 50 / 每批 50 | 2.69 秒 | 2 |
| 并发 100 / 每批 100 | 1.55 秒 | 1 |

这组数据直接推翻了“每节点独立进程”的初始方案。进程启动、配置写入和端口初始化的固定开销，在 100 节点规模下远大于节点本身握手时间。

**结果**

共享内核池成为最终模型。它带来的新约束是：一批节点共用进程，批次启动失败会影响整批；因此批次大小、端口范围和启动超时变成需要显式配置的参数。

**用户验收结论**

用户接受单文件页面 + 六步流程，接受共享内核模型；CLI 作为备用入口保留。

### 3.3 2026-11-03 至 11-04：进度、结果与提取细节

**用户要什么**

测试过程要能看到进度，断线后不能永远停在“进行中”；结果要能直接判断节点是否可用；导出的顺序和文件名要稳定；资产格式要覆盖实际下载到的网页、CSV、JSONL 和裸 IP。

**谁怎么判断**

主协调助手把问题分成三类：状态同步、结果语义、输入兼容。每一类都必须能用页面或文件核对，而不是只看控制台。

**做了什么**

- 测试进度改为 SSE 实时推送，事件带递增序号，支持 `Last-Event-ID` 续传与心跳；
- 修复测试序号一直显示 `[0/X]` 的问题；
- 修复“测速已经结束，页面仍显示进行中”的状态不同步问题；
- 失败原因中文化：`connection_timeout`、`tls_failed`、`speed_failed`、`proxy_error` 等映射为中文，CSV 增加中文原因列，JSON 同时保留原始 `error_type` 与中文原因；
- 自动存盘排序规则固定：测速 + 延迟按速度降序，无速度结果的排在后面；只测延迟时按延迟升序；
- 导出跟随页面当前排序；“按延迟 TXT”“按速度 TXT”则固定各自顺序，不受页面排序影响；
- 导出文件名统一为 `中文用途_YYYYMMDD_HHMMSS.ext`，同秒重复追加 `_2`、`_3`；
- 提取侧支持明文 `IP:端口`、裸 IP 补默认端口、`vless://` 链接、CSV、JSON、JSONL、HTML；
- 国家列兼容多种别名，输出统一为 `🇦🇺-澳大利亚` 这种“国旗-国家”格式；
- 增加三个提取导出：IP、IP+端口、IP+端口+国家；
- 生成侧支持 1～10 条示例模板，逐条校验，失败行给出“第 N 条”的原因；支持随机分配与顺序循环；
- 结果表与预览表增加勾选、全选/反选、已选计数，支持仅测试勾选项、重测勾选项。

**暴露的问题与解决**

- SSE 只发一次或 done 事件丢失，会让前端误判；增加 `/api/state` 轮询兜底。
- JSONL 曾被当成单份 JSON 解析，报 `Extra data`；改为逐行解析。
- CSV 中 `host` 列如果是完整 URL，直接按字段拼国家会得到空值；改为先规范化主机字段，再做国家映射。
- 页面最初用 `Treeview(show="")` 做日志区，内容实际不显示；改为可读的文本/列表控件。
- 进度序号和测速结束状态属于两处独立缺陷，分别修事件序号生成与任务结束状态回写，不是改一个 CSS 就能解决。

**用户验收结论**

用户按页面实际测试后接受上述规则，并继续用真实节点反馈失败原因与导出顺序问题。

### 3.4 2026-11-04：启动器、托盘与发布模块

**用户要什么**

不想每次开命令行；希望双击一个 exe，服务自动启动、浏览器自动打开，窗口可最小化到托盘；另外希望把生成内容或文件快速传到自己已有的文本存储，得到短链接。

**谁怎么判断**

主协调助手要求“窗口关闭”和“进程退出”必须区分清楚，退出必须停服务、释放端口、清理 Xray；编码会话在真实 Windows 桌面上验证托盘、菜单和状态机。

**做了什么**

- `app/launcher.pyw`：Tk 窗口 + Win32 托盘，单实例，服务启停状态机；
- 双击 exe 后自动启动服务、端口监听成功后自动打开浏览器、托盘就绪后自动收进托盘；
- 窗口 X 与最小化都只收进托盘；退出只有窗口“退出”和托盘“退出”两条路径，二者共用清理流程；
- 托盘右键菜单固定四项：显示窗口、打开页面、打开工作目录、退出；
- 服务使用 waitress（8 线程）；未安装时回退 Flask 内置服务器并明确提示；
- 发布模块：可选择文件或生成内容后上传到自建文本存储；回显只使用短链接；
- 短链接格式抽象为 `https://<域名>/<URL编码文件名>?token=<token>`，域名、token、文件名可配置并持久化，文件名支持 `{date}.txt`；
- 设置页与结果页的配置持久化到本地，不在代码里硬编码真实域名或 token。

**结果**

桌面启动器与托盘可用。发布模块成为独立小功能，不影响节点测试主链路。

**暴露的问题与解决**

- `getpass()` 在 Windows 控制台逐字符读取，粘贴会丢失；改为普通输入 + 明确提示，并在 UI 中避免依赖控制台粘贴。
- Windows 10 64 位下 UTF-8 `.bat` 被 cmd 按 GBK 解析，出现乱码；启动脚本改用 PowerShell 或避免中文批处理。
- 直接双击 `file://` 页面无法访问 `127.0.0.1` 的接口；页面与 README 都改为要求通过 `http://127.0.0.1:8765/` 访问。
- Python 3.13 移除了 `ctypes.wintypes.LRESULT`/`HCURSOR`，托盘初始化崩溃；改为兼容的 ctypes 类型/常量。
- 托盘右键菜单最初“有框无字”，改用 `tk.Menu` 后恢复。
- 设置 `Treeview(show="")` 导致日志区空白；改为正常显示的控件。
- 旧 exe 还占用端口时，新页面请求会 404；加入端口占用提示和单实例处理，先停旧进程再启动。

**用户验收结论**

用户接受“窗口 + 托盘 + 自动打开浏览器”的启动方式，并要求源码与 exe 分离、临时产物不进入仓库。

### 3.5 2026-11-04：真实内核检查与打包

**用户要什么**

最终交付一个可直接双击的 exe，同时保留源码；没有内核也能完成导入、提取、生成并导出未测试链接。

**谁怎么判断**

编码会话先跑离线自检，再用真实 Xray 做最小启动检查；主协调助手核对包内外文件边界，确保 `config.json`、内核、日志、临时目录不被误打包。

**做了什么**

- `--selftest` 扩展为 24 项离线检查：固定样例提取、三组提取样本、6 节点生成、缺参报错、模拟延迟/速度/失败分类、CSV/JSON、多种 txt 导出、FOFA 语句、多示例分配、Xray 单节点配置字段、进程清理；
- 增加 `--xray-check`：解析内核路径和版本，用最小 socks 入站真实启动一次，确认端口监听后结束并释放端口；
- 实测 Xray 版本：`Xray 26.10.31 (Xray, Penetrates Everything.) a4a3dff (go1.27.3 windows/amd64)`；
- 启动器增加 `--tray-selftest` 与 `--ui-selftest`，分别验证托盘图标/菜单和真实 Tk + waitress 状态机；
- 使用 PyInstaller 打包：`--onefile --noconsole --noconfirm --name VLESS-Workbench --icon app.ico`，入口 `launcher.pyw`；
- 包内收 `vless_tool`、`web/index.html`、`app.ico`、`config.example.json`、Flask/waitress；包外保留 `config.json`、`app/xray/xray.exe`、`downloads/`、`app/tmp/work/`、`app/logs/`；
- 打包产物复制到根目录，最终 `VLESS-Workbench.exe` 为 16,303,828 字节，约 15.55 MB。

**结果**

源码运行、Web 运行、启动器运行、真实内核启动检查、离线自检、托盘/UI 自检均有独立入口。没有 Xray 时，主流程仍可到“导出未测试链接”，只影响真实延迟/测速。

**暴露的问题与解决**

- `tempfile.mkdtemp` 在权限异常或安全软件拦截时会长时间卡住；改为可控工作目录下的批次子目录，并设置批次结束清理与退出清理。
- 测试批次目录、日志、上传副本原本容易和用户下载文件混在一起；最终把 `downloads/` 只留给用户文件与导出成果，过程文件统一进 `app/tmp/work/`。
- 一次清理曾误删 `downloads` 里 6 个刚生成的结果文件。用户判断它们是测试产物，未要求重做；之后明确目录边界，过程文件不再写入 `downloads/`。

**用户验收结论**

用户接受最终目录分工与打包方式：`downloads` 只放用户文件与导出成果，`app/tmp/work` 放过程文件；exe 作为独立分发物。

### 3.6 2026-11-05：清理、GitHub Desktop 首次提交与发行

**用户要什么**

把源码发布到 GitHub，但本机没有独立 git 命令环境，只有 GitHub Desktop 自带 git；exe 体积较大，不希望直接进仓库。

**谁怎么判断**

主协调助手把“源码版本库”和“二进制发行物”分开：仓库只提交源码与必要模板，exe 走 GitHub Releases 附件。编码会话负责确认忽略规则与运行目录。

**做了什么**

- 清理 `build/`、`dist/`、临时测试目录和缓存；
- `.gitignore` 排除 `config.json`、`downloads/*`（保留 `.gitkeep`）、`app/xray/`、`app/tmp/`、`app/logs/`、`*.exe`、虚拟环境与缓存；
- 通过 GitHub Desktop 完成首次提交，共 27 个文件，包含 `downloads/.gitkeep`；
- 根目录 `VLESS-Workbench.exe` 上传到 GitHub Releases，作为发行附件，不进入仓库历史；
- README 补齐安装、五步 CLI、六步 Web、配置说明、自检、常见问题与合规提示；
- `docs/代码结构说明.md` 作为代码层文档，记录模块、调用关系、路径语义和已知不一致。

**结果**

仓库与发行物分离：克隆仓库得到源码、配置模板与示例数据；下载 Release 附件得到可双击 exe。真实 FOFA 域名、token、邮箱、密钥均未写入文档或源码。

**用户验收结论**

用户完成首次提交与 Release 挂载，接受“源码仓库 + Release exe”的发布结构。

## 4. 关键决策与取舍

| 决策点 | 初始方案 | 最终方案 | 原因与代价 |
| --- | --- | --- | --- |
| FOFA 数据获取 | 官方 API + email/key，网页采集兜底 | 只生成查询语句与搜索链接，用户手动搜索/下载/导入 | 免费账号字段与额度限制多，凭据维护成本高；代价是第 1 步不再全自动 |
| 凭据管理 | `credentials.py`、`--setup`、配置 email/key/session | 全部删除 | 工具不再承担账号安全与登录态问题；代价是无法直接调用 API |
| 测试内核模型 | 每节点一个 Xray 进程、独立配置 | 每 `kernel_batch` 个节点共享一个进程和一份配置 | 100 节点启动开销从 84.91 秒降到 2.69/1.55 秒；代价是批次耦合 |
| 延迟/测速并发 | 一个并发数 | 延迟 50、测速 5 分开 | 延迟不等带宽，测速会互相抢带宽；代价是两阶段调度更复杂 |
| Web 页面 | 参考 PEN 风格自研 | 在 Cloudflare EDT 导航页存档上改造，单文件 `index.html` | 减少重复造 UI，保留单文件零外部依赖；代价是需处理历史样式与交互 |
| 页面流程 | 与 CLI 相同的五步 | Web 六个可见步骤，CLI 五步 | “FOFA 搜索”和“导入资产”分开更适合网页；业务层仍归入导入 |
| 过程文件位置 | 与下载文件混放 | `downloads/` 给用户与导出，`app/tmp/work/` 放过程文件 | 避免误删与污染；代价是多一层路径约定 |
| 结果保存 | 用户手动点保存 | 测试结束自动存 CSV+JSON，另提供手动导出 | 防止结果丢失；代价是需处理 0 成功节点不写空文件 |
| 导出排序 | 固定延迟排序 | 跟随页面排序；固定“按延迟/按速度”按钮另算 | 用户希望导出与当前视图一致；代价是排序规则必须写清 |
| 分发方式 | 源码 + exe 一起提交 | 源码进仓库，exe 进 Releases | 避免 15.55 MB 二进制反复进入历史；代价是用户需从 Release 下载 |
| 运行形态 | 纯 CLI | CLI + 本地 Web + Tk 启动器 + 托盘 | 降低批量操作门槛；代价是启动器与端口状态机需要额外自检 |

## 6. 踩坑清单

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| 控制台凭据输入粘贴时逐字符丢失 | `getpass()` 在 Windows 控制台的读取方式 | 放弃凭据输入路线，后续整套删除；普通输入不再依赖隐藏读取 |
| UTF-8 的 `.bat` 在 Windows 10 64 位运行乱码 | cmd 按 GBK 解析批处理文件 | 启动脚本改用 PowerShell/避免中文批处理 |
| 双击页面后接口全不可用 | `file://` 页面不能访问 `127.0.0.1` 服务 | 强制通过 `http://127.0.0.1:8765/` 访问，并在页面给出启动提示 |
| 临时目录创建偶尔长时间卡住 | `tempfile.mkdtemp` 遇到权限/安全软件拦截 | 使用受控 `app/tmp/work` 批次目录，批次结束/退出清理 |
| Python 3.13 下托盘初始化崩溃 | `ctypes.wintypes.LRESULT`/`HCURSOR` 被移除 | 改用兼容类型/常量 |
| 托盘右键菜单有框无字 | 原生菜单与托盘回调组合不兼容 | 改用 `tk.Menu` |
| 日志区一片空白 | `Treeview(show="")` 隐藏了所有列 | 改为正常显示的文本/控件 |
| JSONL 报 `Extra data` | 把多行 JSON 当成单份 JSON 解析 | 识别 JSONL 并逐行解析 |
| CSV 国家列全空 | `host` 列是完整 URL，字段拼接前未规范化 | 先提取/规范化主机，再做国家别名映射 |
| 旧 exe 占用端口导致前端 404 | 单实例与端口释放逻辑不完整 | 启动前检查端口、提示占用、单实例激活/退出 |
| 测速结束页面仍显示“进行中” | done 事件丢失或状态未回写 | `/api/state` 轮询兜底 + 任务结束状态回写 |
| 测试序号一直 `[0/X]` | 进度事件序号没有随完成数递增 | 修正事件序号生成 |
| 清理时误删 `downloads` 下 6 个结果文件 | 过程文件与用户目录混在一起 | 用户判定为测试产物、未重做；之后严格分离 `downloads` 与 `app/tmp/work` |
| 100 节点测试耗时 84.91 秒 | 每节点独立启动内核，固定开销叠加 | 改为共享内核池，降到 2.69/1.55 秒 |

## 9. 已知局限与后续想法

- 本地 Web 默认只监听 `127.0.0.1`，没有登录鉴权；改成 `0.0.0.0` 会暴露到局域网，当前不适合不可信网络。
- FOFA 路线是“生成语句 + 手动搜索/导入”，不自动调用 API；这降低了凭据风险，也降低了自动化程度。
- 共享内核池提升速度，但批次内耦合：批次启动失败、端口不足会影响整批。后续可做自适应批次、失败批次拆分。
- 测速结果受目标站点限速与本地带宽影响，不能仅凭 Mbps 判断节点长期质量；后续可增加多次采样与中位数。
- exe 未做代码签名，分发时需说明 SmartScreen 风险。
- 自检覆盖了模拟内核与配置字段，不覆盖真实公网节点的长期稳定性；真实测试仍需用户提供合法目标。
- `docs/代码结构说明.md` 第 9 节保留了一批历史不一致清单，部分描述针对早期版本；当前行为以该文档主体、README 与最终源码为准，后续可单独清理历史条目。
